## 核心区别

从软件角度看：

- **电平触发**：中断请求像一个“持续存在的条件”。只要设备仍然保持中断线有效，中断就可能持续处于 pending，甚至 ISR 返回后立即再次进入。
- **边沿触发**：中断请求像一个“事件通知”。当信号发生上升沿或下降沿时，控制器记录一次事件；即使信号很快恢复，pending 通常也会保留，等待软件处理。

可以简单记成：

> 电平触发关心“现在是否还需要处理”；边沿触发关心“刚才是否发生过一次事件”。

---

## 1. 电平触发的软件行为

假设某个 UART 收到数据后，把中断线拉高：

```text
UART_RX 有数据
    ↓
IRQ = 1
    ↓
CPU 进入 ISR
```

如果软件只清除了中断控制器的 pending，但 UART 内部仍然有数据：

```text
UART_RX 有数据
IRQ 仍然为 1
```

那么 ISR 返回后，中断控制器可能再次发现中断线有效，于是再次进入 ISR。

因此，电平触发的 ISR 通常要：

1. 查询设备状态；
2. 处理导致中断的条件；
3. 清除或消除设备侧的中断源；
4. 最后清除控制器 pending 或完成中断处理。

伪代码：

```c
void uart_isr(void)
{
    // 先处理设备侧的实际中断原因
    while (uart_rx_ready()) {
        char c = uart_read();
        process_char(c);
    }

    // 某些设备还需要显式清除中断状态
    uart_clear_irq();

    // 根据具体中断控制器实现执行 EOI/complete
}
```

### 电平触发最重要的注意点

**不要只清控制器，不清设备。**

错误示例：

```c
void isr(void)
{
    interrupt_controller_clear_pending();
    return;
}
```

如果 UART、GPIO 或 DMA 仍然保持中断条件，软件返回后中断可能立刻再次触发，造成：

- ISR 不断重复进入；
- CPU 被中断占满；
- 看起来像“中断风暴”。

---

## 2. 边沿触发的软件行为

假设 GPIO 从低电平变成高电平：

```text
GPIO: 0 ───────┐
               └──── 1
               ↑
             上升沿
```

控制器检测到这个变化后，把 pending 位置上：

```text
pending = 1
```

即使 GPIO 很快恢复为低电平：

```text
GPIO: 0 ───────┐   ┌──── 0
               └───┘
                 ↑
              曾经发生过边沿
```

pending 通常仍会保持，直到软件清除或完成该中断。

因此，边沿触发的 ISR 通常需要：

1. 读取设备状态；
2. 处理这个事件；
3. 清除设备事件标志；
4. 清除控制器中的 pending，或者执行 complete。

伪代码：

```c
void gpio_isr(void)
{
    uint32_t status = gpio_get_event_status();

    // 清除设备侧已经捕获的事件
    gpio_clear_event(status);

    if (status & GPIO_BUTTON_RISING) {
        handle_button_press();
    }

    // 根据具体控制器实现清除 pending 或执行 EOI
}
```

## 3. 两者在“清中断”上的差异

| 对比项 | 电平触发 | 边沿触发 |
|---|---|---|
| 触发依据 | 信号当前是否有效 | 信号是否发生变化 |
| 中断线是否需要持续有效 | 通常需要 | 不需要 |
| 短脉冲能否被记录 | 取决于硬件，可能丢失 | 通常可被锁存 |
| ISR 返回后是否可能再次触发 | 如果源仍有效，会再次触发 | 通常不会因原来的边沿重复触发 |
| 软件重点 | 消除中断产生条件 | 处理并清除事件记录 |
| 常见风险 | 中断风暴 | 丢边沿、事件合并、竞态 |

## 4. 典型例子：UART 和 GPIO

### UART：通常适合电平触发

UART 接收 FIFO 中有数据时，中断保持有效：

```text
FIFO 非空 → IRQ 有效
FIFO 为空 → IRQ 无效
```

这天然符合电平触发的语义，因为只要 FIFO 还有数据，就应该继续处理。

软件通常会循环读取：

```c
while (uart_rx_fifo_not_empty()) {
    read_uart();
}
```

如果只读一个字节，FIFO 仍然非空，退出 ISR 后中断会再次到来。这通常是合理的。

---

### 按键 GPIO：通常适合边沿触发

按键按下时产生一次边沿：

```text
未按下 → 按下
```

软件处理一次按键事件即可，不需要按键一直保持某种电平来表示“中断请求”。

不过真实按键有机械抖动，可能产生多个边沿，因此还需要：

- 硬件去抖；
- 软件延时去抖；
- 定时器确认；
- 屏蔽后再恢复中断。

---

## 5. 共享中断时的差别

多个设备共享同一个 IRQ 时，两种触发方式的处理方式也不同。

### 共享的电平触发

假设设备 A 和设备 B 共用一条中断线：

```text
A IRQ ─┐
       ├── IRQ
B IRQ ─┘
```

ISR 通常要轮询所有设备：

```c
void shared_isr(void)
{
    if (device_a_irq_active())
        device_a_isr();

    if (device_b_irq_active())
        device_b_isr();
}
```

只要还有一个设备保持中断有效，共享线就保持有效。因此软件必须把所有当前有效的源都处理掉。

---

### 共享的边沿触发

共享边沿触发通常更麻烦。

如果 A 已经产生边沿，线路发生一次变化；随后 B 也产生事件，但共享线路可能没有产生一个新的、可被可靠检测的边沿，或者多个事件被合并。

因此：

- 边沿触发不太适合简单的共享 IRQ；
- 每个设备最好有独立中断线；
- 如果必须共享，需要硬件提供可靠的事件状态寄存器，并由软件扫描所有设备。

---

## 6. 一个容易混淆的点：控制器配置和设备行为是两回事

“电平触发还是边沿触发”通常涉及两层：

### 中断控制器侧

例如配置为：

```text
IRQ 5 = level-triggered
IRQ 6 = edge-triggered
```

### 设备侧

设备可能有：

- 中断状态寄存器；
- 中断屏蔽寄存器；
- 中断清除寄存器；
- FIFO 状态；
- 边沿事件捕获寄存器。

必须保证两边的语义匹配。

例如，设备实际输出的是一个短脉冲，但控制器却配置成电平触发，可能导致控制器无法正确观察到持续有效状态。反过来，设备保持中断电平有效，而控制器配置成边沿触发，也可能只捕获第一次边沿，后续状态变化无法按预期工作。

## 7. ISR 中清除顺序为什么重要？

常见原则是：

### 电平触发

```text
读取设备状态
    ↓
处理数据或错误
    ↓
清除设备中断源
    ↓
清除/完成控制器中断
    ↓
返回
```

因为必须先让外设的中断条件消失。

### 边沿触发

```text
读取设备事件状态
    ↓
清除设备事件标志
    ↓
清除/完成控制器 pending
    ↓
返回
```

但具体顺序取决于硬件手册。有些设备要求先读状态再写清除寄存器，有些设备要求写特定值，有些控制器还规定必须先 claim 再 complete。

所以实际驱动中应以芯片手册为准。

## 8. 常见问题

### 问题一：电平触发会不会重复处理中断？

会，但这不一定是错误。

如果中断源仍然存在，例如：

```text
UART FIFO 仍有数据
DMA 错误状态仍未清除
GPIO 输入仍处于有效电平
```

那么再次进入 ISR 是合理行为。

---

### 问题二：边沿触发会不会丢事件？

可能。

如果多个边沿在软件处理前发生，而硬件只有一个 pending 位：

```text
边沿 1 → pending = 1
边沿 2 → 仍然 pending = 1
边沿 3 → 仍然 pending = 1
```

软件可能只知道“至少发生过一次”，而不知道具体发生了三次。

因此，如果不能丢事件，设备通常需要提供：

- FIFO；
- 计数器；
- 事件队列；
- 多位事件状态寄存器。

---

### 问题三：边沿触发是不是一定比电平触发快？

不一定。

边沿触发的硬件语义可能减少某些重复检查，但实际延迟还取决于：

- 中断控制器；
- CPU 入口；
- 是否向量化；
- cache；
- ISR 保存恢复；
- 总线访问；
- RTOS 调度。

不能简单认为边沿触发一定更快。

---

## 总结

从软件设计角度：

- **电平触发**：ISR 必须把“中断条件”处理掉，否则返回后可能马上再次触发。
- **边沿触发**：ISR 必须处理并清除“事件记录”，但信号本身不需要继续保持有效。
- 电平触发适合 UART、DMA、FIFO 等“条件持续存在”的设备。
- 边沿触发适合按键、脉冲、状态变化等“一次性事件”。
- 电平触发更容易出现中断风暴；边沿触发更需要防止丢边沿和事件合并。
- 在 CLIC 或其他中断控制器中，最终仍要结合具体芯片对 pending、ack、clear、complete 的定义来写 ISR。
